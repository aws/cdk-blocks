Behind every built-in front door, the server now sees the public host, scheme and client address. Hosting rewrites each request from values the door itself sets before the server sees it: `Host` and `x-forwarded-host` name the public host, `X-Forwarded-For` holds only the client's address, and `x-forwarded-proto` is the viewer's scheme, also behind the stacked door, whose edge → router hop may be plain HTTP. Behind the CloudFront and stacked doors the client address comes from a new `x-blocks-viewer-ip` header that the door's viewer-request function sets from the viewer's address (and that never reaches the server); behind API Gateway it is the event's `sourceIp`; behind the ALB, the entry the ALB appended. Nothing a client sends in `X-Forwarded-For` becomes the client address. Nuxt's `useRequestURL()` behind the CloudFront door is the public URL instead of the origin's, and SvelteKit's `getClientAddress()` is the client's address instead of a loopback or link-local one (`ADDRESS_HEADER` and `XFF_DEPTH` are set, on Lambda and on Web Functions; they are dropped where requests aren't rewritten, so a bring-your-own door keeps reading the socket). Astro reads these headers once `security.allowedDomains` names the host; the README's "The host the server sees" lists what each door is trusted for.

What changes for a server behind a built-in door: `Host` is the public host instead of the origin's; `X-Forwarded-For` is one address instead of the full chain; behind the CloudFront and stacked doors, a Lambda event's `requestContext.identity.sourceIp` / `requestContext.http.sourceIp` is the client's address instead of CloudFront's. If your app reads `Host` to find the origin, or walks the `X-Forwarded-For` chain, check it against these values.
